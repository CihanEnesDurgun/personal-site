# 📄 Versiyon Notları - v0.2.1

_Yayın Tarihi: 2 Ağustos 2026_

## 🌟 Genel Bakış

`v0.2.1`, projenin **git tabanlı deploy hattıyla ilk kez canlıya alındığı** sürümdür.
Önceki sürüm (`v0.2.0`) kod tarafında yayına hazır hale getirilmişti ama sunucuya hiç
uygulanmamıştı; sunucuda zip ile elle yüklenmiş, aylar öncesine ait bir sürüm çalışıyordu.

Bu sürümle birlikte "yerelde geliştir → GitHub'a gönder → sunucuda tek komut" akışı
kuruldu ve uçtan uca doğrulandı. Ayrıca deploy sonrası yapılan ilk gerçek kod
değişikliğiyle (tema düzeltmesi) akışın çalıştığı ikinci kez teyit edildi.

## 🚀 İlk Git Tabanlı Deploy

### Başlangıç durumu

Sunucudaki (`~/site`) sürüm o kadar eskiydi ki `project.html` ve `projects.html`
dosyaları bile yoktu — projeler sayfası o dönemde henüz eklenmemişti. Yanında birikmiş
artık dosyalar vardı (`_diff.txt`, `test-marked.js`, `walkthrough.md.resolved`,
`config.json`).

cPanel tarafında kurulumun bir kısmı önceki denemelerden kalmıştı:

| Bileşen | Durum |
|---|---|
| Node.js uygulaması (`nodevenv/site/20/`) | Kuruluydu — 20.20.2, Production modda |
| `~/repositories` klasörü | Vardı ama içinde `personal-site` deposu **yoktu** |
| `~/site_old_20260529-204501` | Önceki denemeden kalan yedek |

### Kurulan hat

1. **Yedek alındı.** Deploy'a dokunmadan önce `~/site` klasörünün tam zip kopyası
   çıkarıldı. Canlı içerik (`content/`, `images/`, `data/`) yalnızca sunucuda yaşadığı
   için bu adım pazarlık konusu değildi.
2. **Git deposu oluşturuldu.** cPanel → Git Version Control → Create ile
   `repositories/personal-site` yoluna klonlandı. Repo public olduğu için
   `docs/deployment/cpanel-deploy.md`'de anlatılan **GitHub token adımına gerek kalmadı**.
3. **Deploy tetiklendi.** `scripts/server-deploy.sh` cPanel Terminal'den çalıştırıldı;
   `git pull` + `uapi VersionControlDeployment create` ile `.cpanel.yml` devreye girdi.
   Tüm adımlar `exit code 0` ile tamamlandı.

### Doğrulanan tasarım kuralı

Deploy'un **yalnızca kodu taşıdığı** canlı ortamda teyit edildi: `content/`, `images/`,
`data/` klasörlerine hiç dokunulmadı. Sunucuda duran iki yazı, görseller, yorumlar ve
istatistikler olduğu gibi kaldı; yalnızca kod dosyaları güncellendi.

## 🔍 Deploy Sırasında Ortaya Çıkan İki Bulgu

### 1. Sunucuda `.env` dosyası yok — ve gerekmiyor

`docs/deployment/cpanel-deploy.md` "sunucuda `.env` oluştur" diyor, ancak gerçek kurulum
öyle değil: zorunlu ortam değişkenleri **cPanel → Setup Node.js App → Environment
variables** bölümünde tanımlı.

| Değişken | Değer |
|---|---|
| `JWT_SECRET` | 64 karakter (min. 32 gerekli) |
| `BCRYPT_SALT_ROUNDS` | 12 |
| `NODE_ENV` | production |
| `PORT` | 3000 |

Passenger bunları `process.env`'e geçiriyor; `dotenv` mevcut `process.env` değerlerini
ezmediği için çakışma olmuyor. `server.js` yalnızca `JWT_SECRET` ve `BCRYPT_SALT_ROUNDS`
değişkenlerini zorunlu tutuyor, ikisi de karşılanıyor.

> **Doküman güncellenmeli:** `cpanel-deploy.md`'deki 4. adım gerçeği yansıtmıyor.

### 2. `content/projects.json` sunucuda yoktu

Deploy sonrası projeler sayfası `Projeler yüklenemedi: Unexpected token '<'` hatası verdi.
Sebep: projeler özelliği eski sürümde yoktu, `content/` klasörü de (doğru biçimde) deploy
kapsamı dışında — dolayısıyla dosya sunucuda hiç oluşmamıştı. İstemci JSON beklerken 404
HTML sayfası alıyordu.

Çözüm: sunucuda `content/projects.json` boş liste (`[]`) olarak ve `content/projects/`
klasörü elle oluşturuldu.

> **Genel ders:** Yeni bir özellik `content/` altında yeni bir dosya bekliyorsa, o dosya
> deploy ile gelmez — sunucuda bir kez elle oluşturulması gerekir. Bu, deploy'un içerik
> klasörlerine dokunmama kuralının kaçınılmaz yan etkisidir.

## 🎨 Düzeltildi — Sayfa Açılışındaki Açık Tema Parlaması

Deploy hattı kurulduktan sonra yapılan ilk gerçek kod değişikliği. Sayfalar bir an açık
temada parlayıp sonra koyuya dönüyordu; gizli sekmede ve farklı tarayıcılarda da
tekrarlanıyordu.

İnceleme sonucunda **varsayılan temanın zaten koyu olduğu** ortaya çıktı
(`theme-manager.js` → `getCurrentTheme()` kayıtlı tercih yoksa `'dark'` döner). Sorun
varsayılanda değil, iki ayrı yerdeydi:

### Sorun 1 — Koyu tema ilk boyamadan sonra uygulanıyordu

`styles.css` içinde `:root` açık renklerle başlar; koyu renkler ancak `<html>` etiketine
`dark` sınıfı eklendiğinde devreye girer. O sınıfı ekleyen JavaScript ise sayfa
çizildikten **ve** `/api/theme` isteği tamamlandıktan sonra çalışıyordu
(`scripts.js` → `DOMContentLoaded` → `await loadCustomTheme()` → `new ThemeManager()`).

Ölçülen `/api/theme` yanıt süresi ~150 ms; sayfa yükleme süresiyle birlikte beyaz
pencere 150–300 ms sürüyordu.

**Çözüm:** Beş sayfanın (`index`, `blog`, `post`, `project`, `projects`) `<head>`
bölümüne, ilk boyamadan önce çalışan küçük bir betik eklendi. Betik kayıtlı tercihe bakar
ve `light` değilse `dark` sınıfını hemen yerleştirir. `localStorage` erişimi engelliyse
(bazı gizlilik ayarları) `catch` bloğu yine koyuya düşer.

### Sorun 2 — Tema yükleyicisi koşulsuz açık renk yazıyordu

`theme-manager.js` → `applyThemeVariables()` sunucudan gelen temayı uygularken `--bg`,
`--ink`, `--panel` gibi değişkenlere **her zaman açık** paleti yazıyordu. Bunlar satır içi
stil olduğu için CSS'teki `:root.dark` kuralından daha yüksek önceliğe sahip — yani koyu
tema seçiliyken bile araya bir açık kare giriyordu. `setTheme()` hemen ardından doğru
renkleri yazıp durumu düzeltiyor, ama arada gözle görülür bir sıçrama kalıyordu.

**Çözüm:** Fonksiyon artık o an aktif olan temanın paletini yazıyor.

### Doğrulama

Yerel sunucuda `localStorage` temizlenerek "ilk kez giren ziyaretçi" senaryosu simüle
edildi:

| Senaryo | Beklenen | Sonuç |
|---|---|---|
| İlk ziyaret (kayıtlı tercih yok) | Koyu | ✅ `--bg: #0b0d0f` |
| Açık tema seçilip sayfa yenilenir | Açık kalır | ✅ `--bg: #fbfaf4` |
| `blog.html` ilk ziyaret | Koyu | ✅ `--bg: #0b0d0f` |
| Konsol hataları | Yok | ✅ Yok |

Ziyaretçinin kendi tercihi korunuyor — varsayılan koyu, isteyen açığa çekebiliyor.

  çelişiyor; ortam değişkenlerinin cPanel panelinde tutulduğu yazılmalı.

**Temizlik** (canlı ortam birkaç gün sorunsuz çalıştıktan sonra)
- `~/site.zip` ve `~/site_old_20260529-204501` yedekleri.
- `~/site` içindeki artık dosyalar: `_diff.txt`, `test-marked.js`,
  `walkthrough.md.resolved`, `config.json`.
- `.cpanel.yml` dosyaları `cp -Rf` ile kopyalıyor, yani silinen dosyalar sunucuda kalıyor.
  `src/` ve `admin/` altında eski sürümden artakalan kullanılmayan dosyalar olabilir.

## 📋 Bundan Sonraki Günlük Akış

**Kod değişikliği yayınlama:**

```bash
# 1) yerelde
git add . && git commit -m "..." && git push

# 2) cPanel > Terminal
bash ~/repositories/personal-site/scripts/server-deploy.sh
```

**İçerik (yazı, proje) ekleme:** doğrudan canlı sitedeki admin panelinden. Bu içerik
sunucuda yaşar, GitHub'a gitmez ve sonraki deploy'lar tarafından **ezilmez**.

**İçerik yedeği:** ara sıra `npm run content:pull` çalıştırılıp `content/` ve `images/`
git'e işlenebilir. Deploy için gerekli değildir, yalnızca yedek amaçlıdır. Sunucudan
GitHub'a otomatik geri senkron **yoktur** — bu bilinçli bir tercihtir; otomatik push
sunucuda yazma yetkili bir GitHub token'ı bulundurmayı gerektirirdi.
